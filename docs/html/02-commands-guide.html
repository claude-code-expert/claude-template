개념커맨드란 + 파일 구조

슬래시 커맨드는 거창한 게 아니다. .claude/commands/<name>.md 파일 한 장이 곧 커맨드 하나이고, 세션에서 /<name> 을 치면 그 파일 본문이 프롬프트로 주입된다. 매번 손으로 풀어 쓰던 지시문을 파일에 굳혀 두고 재사용하는 장치다. 파일 이름이 곧 호출 이름이라, git-commit.md 는 /git-commit 이 된다.

파일은 두 부분으로 나뉜다. 위쪽 YAML frontmatter(메타데이터)와 아래쪽 body(Claude가 실제로 따를 지시문)다.

.claude/commands/<name>.md — 뼈대
---
description: /help 목록에 뜨는 한 줄 설명
allowed-tools: Bash(git status:*)
argument-hint: "[base-branch]"
---

여기부터가 body. Claude가 이 지시문을 그대로 따른다.
사용자가 넘긴 인자는 $ARGUMENTS 로 치환된다.
frontmatter 필드의미없으면
description/help 목록과 / 자동완성에 뜨는 설명. 이 커맨드가 뭘 하는지 한 줄로.목록에 설명이 비어 뜬다
allowed-tools이 커맨드가 확인 없이 쓸 수 있는 도구 화이트리스트. Bash(git push:*) 처럼 명령 단위로 좁힐 수 있다.목록 밖 도구 사용 시 매번 권한 프롬프트
argument-hint/ 자동완성에서 뒤에 뭘 넘길지 보여주는 인자 힌트. 실행에는 영향 없고 UX용.힌트 없이 이름만 뜬다

body 안의 $ARGUMENTS 는 사용자가 커맨드 이름 뒤에 붙인 문자열로 그대로 치환된다. /git-pr develop 이면 $ARGUMENTS = develop 이다. 인자를 안 넘기면 빈 문자열이 되므로, body에서 "비어 있으면 기본값" 식으로 처리해야 한다.

커맨드 vs 스킬

커맨드는 사용자가 / 로 명시적으로 호출해야 뜬다. 스킬(강의 3편)은 발화 내용에 맞으면 자동 발동한다. "내가 언제 부를지 정한다" = 커맨드, "조건 맞으면 알아서 뜬다" = 스킬.

제작만드는 법 — 기능 지정 + 생성 프롬프트

커맨드를 새로 만들 때 먼저 다섯 가지를 정한다. 이걸 안 정하고 "커맨드 만들어줘" 하면 Claude가 임의로 채운다.

  • 이름 — 파일명이자 호출 이름(/deploy-staging 이면 deploy-staging.md).
  • 설명 — description 한 줄. 목록에서 이걸 보고 고른다.
  • 필요한 도구 권한 — allowed-tools 에 넣을 최소 도구. 넓게 Bash 하나로 열지, Bash(git push:*) 처럼 명령까지 좁힐지.
  • 인자 유무 — $ARGUMENTS 를 쓸지, 쓴다면 argument-hint 로 힌트를 줄지.
  • 본문 지시 — Claude가 따를 실제 절차. 순서·기본값·하지 말 것까지.

정한 뒤에는 손으로 파일을 찍기보다 Claude에게 만들게 하는 편이 빠르다. 아래 템플릿의 빈칸만 채워 붙여넣는다.

복붙 생성 프롬프트 템플릿
.claude/commands/<이름>.md 커맨드를 만들어줘.

- 하는 일: <한 줄 요약 + 절차>
- 필요한 도구: <예: git add, git commit, gh pr create>
- 인자: <없음 / $ARGUMENTS 로 base 브랜치를 받음>

frontmatter 의 allowed-tools 로 권한을 최소화하고,
본문은 토큰 절약을 위해 불필요한 출력(diff 전문 등)을
읽지 않도록 지시해줘. description 도 /help 에 뜰 한 줄로 채워줘.
판단

allowed-tools 는 좁을수록 안전하다. Bash 로 통째 열면 그 커맨드가 rm 이든 curl 이든 확인 없이 돌릴 수 있다. push 전용 커맨드라면 Bash(git push:*) 처럼 한 명령으로 못 박아, 실수나 오작동이 나가는 범위를 원천 차단하라. 넓게 여는 건 /check 처럼 프로젝트마다 도구가 달라 미리 특정할 수 없을 때만.

실제 코드커맨드 코드 4종

이 템플릿에 실제로 들어 있는 커맨드 네 개다. 공통 설계 축은 하나 — 토큰 절약. Claude가 도구를 거쳐 명령을 여러 번 나눠 실행하고 그 출력을 다 읽으면 컨텍스트가 빠르게 찬다. 그래서 명령을 && 로 묶어 한 번에 실행하고, diff 전문 대신 요약만 읽게 지시한다.

1. git-commit

.claude/commands/git-commit.md
---
description: 현재 브랜치에서 변경사항을 add + commit
allowed-tools: Bash(git add:*), Bash(git commit:*), Bash(git status:*), Bash(git diff:*), Bash(git branch:*)
---

현재 브랜치에 변경사항을 커밋한다. 토큰 절약을 위해 아래 순서로 git 명령을 직접 실행한다.

1. `git add -A && git status --short && git diff --staged --stat` 를 한 번에 실행해 스테이징 + 변경 요약을 파악한다. (diff 전문을 읽지 말 것)
2. 요약만으로 커밋 메시지 한 줄을 작성한다. 필요할 때만 `git diff --staged` 로 세부를 본다.
3. `git commit -m "<메시지>"` 로 현재 브랜치에 커밋한다.

$ARGUMENTS 가 있으면 그것을 커밋 메시지로 사용한다.

allowed-tools 를 git 하위 명령들로만 좁혀, 이 커맨드가 push나 다른 셸 명령으로 새는 걸 막는다. 본문의 핵심은 1번 — add·status·diff --stat 를 && 로 한 번에 돌려 왕복 횟수를 줄이고, --stat(파일별 증감 요약)만 읽어 diff 전문을 컨텍스트에 안 올린다. 메시지를 안 넘기면 그 요약으로 Claude가 한 줄을 짓고, $ARGUMENTS 로 넘기면 그걸 그대로 메시지로 쓴다.

2. git-push

.claude/commands/git-push.md
---
description: 현재 브랜치를 origin에 push
allowed-tools: Bash(git push:*)
---

현재 브랜치를 그대로 origin에 push 한다. 별도 확인 없이 아래 한 줄을 실행한다.

`git push -u origin HEAD`

네 개 중 가장 단순하다. allowed-tools 가 Bash(git push:*) 딱 하나 — push 외에는 아무것도 못 한다. 좁은 권한의 교과서적 예다. HEAD 로 현재 브랜치를 그대로 밀고 -u 로 업스트림을 걸어, 이후엔 인자 없는 git push 만으로도 되게 한다. 읽을 출력 자체가 없어 토큰 소모도 최소다.

3. git-pr

.claude/commands/git-pr.md
---
description: commit + push 후 PR 생성 (기본 대상 브랜치 develop)
argument-hint: "[base-branch]"
allowed-tools: Bash(git add:*), Bash(git commit:*), Bash(git status:*), Bash(git diff:*), Bash(git push:*), Bash(git branch:*), Bash(gh pr create:*), Bash(gh pr view:*)
---

commit → push → PR 생성을 한 번에 수행한다. 대상(base) 브랜치는 `$ARGUMENTS`, 없으면 `develop`.

토큰 절약을 위해 git 명령을 직접 실행한다.

1. `git add -A && git status --short && git diff --staged --stat` 로 스테이징 + 요약 파악.
2. 요약으로 커밋 메시지 한 줄 작성 → `git commit -m "<메시지>"`. (변경 없으면 커밋 건너뜀)
3. `git push -u origin HEAD` 로 현재 브랜치 push.
4. `gh pr create --base <base> --head <현재브랜치> --fill` 로 PR 생성.
   - `<base>` = `$ARGUMENTS` 값, 비어있으면 `develop`.
   - 이미 열린 PR이 있으면 `gh pr view --web` 로 안내만 한다.

앞의 두 커맨드를 한 흐름으로 엮은 것 — commit → push → PR을 순서대로 밟는다. 그래서 allowed-tools 도 git 계열 + gh pr create·gh pr view 까지 넓게 잡는다. argument-hint: "[base-branch]" 덕분에 자동완성에서 base를 받는다는 게 보인다. 인자 처리가 이 파일의 핵심 — $ARGUMENTS 가 base 브랜치가 되고, 비면 develop 로 떨어진다. 토큰 절약 장치는 git-commit과 동일하게 --stat 요약만 읽는 것이고, "변경 없으면 커밋 건너뜀", "이미 PR 있으면 새로 안 만들고 --web 안내만" 같은 방어 분기까지 본문에 못 박아 헛돎을 막는다.

4. check

.claude/commands/check.md
---
description: lint + typecheck + test 를 한 번에 돌리고 실패만 보고
allowed-tools: Bash
---

프로젝트의 품질 게이트(lint · typecheck · test)를 실행하고 **실패한 것만** 보고한다.
토큰 절약이 목적이므로 성공한 단계는 출력을 읽거나 요약하지 말 것.

1. 프로젝트 종류를 한 번에 감지한다:
   `ls package.json pyproject.toml go.mod Cargo.toml Makefile 2>/dev/null`
2. 감지 결과에 맞는 명령을 `&&` 로 묶어 **한 번에** 실행한다. 대표 매핑:
   - **Node** (`package.json`): `npm run lint && npm run typecheck && npm test`
     (스크립트가 없으면 `package.json` 의 `scripts` 를 보고 있는 것만 실행)
   - **Python** (`pyproject.toml`): `ruff check . && mypy . && pytest -q`
   - **Go** (`go.mod`): `go vet ./... && go build ./... && go test ./...`
   - **Rust** (`Cargo.toml`): `cargo clippy && cargo test`
   - **Makefile** 에 `lint`/`test` 타깃이 있으면 그걸 우선 사용.
3. `$ARGUMENTS` 가 있으면 그 명령을 대신 실행한다 (예: `/check pnpm test`).
4. 보고 규칙:
   - 전부 통과 → **"✅ check passed"** 한 줄만.
   - 실패 → 실패한 단계 이름 + 에러 핵심 라인만. 통과한 단계의 로그는 언급하지 않는다.

명령이 없거나 감지 안 되면 무엇을 돌려야 할지 한 줄로 되묻는다.

여기만 allowed-tools: Bash 로 통째 열려 있다. 이유는 명확하다 — 프로젝트가 Node인지 Go인지 실행 전엔 모르니 도구를 미리 특정할 수 없다. 넓은 권한은 "정말 특정 불가"일 때만 쓴다는 2절 판단의 반대 사례다. 토큰 절약이 이 파일에선 특히 노골적이다 — 감지·실행을 && 로 한 번에 묶고, 성공한 단계 로그는 아예 읽지 말라고 못 박고, 다 통과하면 ✅ check passed 한 줄만 뱉게 한다. 로그 폭탄이 컨텍스트를 먹는 걸 원천 차단하는 설계다. $ARGUMENTS 로 /check pnpm test 처럼 명령을 직접 넘기면 감지를 건너뛰고 그걸 실행한다.

사용실행·발화 방법

세션 입력창에 슬래시로 친다. 인자는 이름 뒤에 공백으로 붙이면 그대로 $ARGUMENTS 에 들어간다.

Claude Code 세션
# 인자 없이
/git-commit
/git-push

# 인자 있게 — 뒤 문자열이 통째로 $ARGUMENTS
/git-commit 로그인 버그 수정
/git-pr develop          # $ARGUMENTS = "develop" → PR base
/check pnpm test         # $ARGUMENTS = "pnpm test" → 이 명령 실행

흐름을 정리하면 이렇다. /git-pr develop 을 치면 Claude가 git-pr.md body를 읽고, 그 안의 $ARGUMENTS 자리에 develop 이 박힌 상태로 지시를 따른다. 인자를 생략한 /git-pr 이면 $ARGUMENTS 는 빈 문자열이 되고, body의 "없으면 develop" 규칙이 작동한다. 같은 커맨드라도 인자에 따라 동작이 갈리는 건 전적으로 body가 $ARGUMENTS 를 어떻게 처리하느냐에 달렸다.

발견

입력창에 / 만 치면 등록된 커맨드가 목록으로 뜬다. 각 줄에 description 이 붙어 뭘 하는지 보이고, argument-hint 가 있으면 /git-pr [base-branch] 처럼 뒤에 뭘 넘길지 자동완성에 함께 뜬다. /help 로도 전체 목록을 볼 수 있다.

검증호출 테스트

새 커맨드 파일을 만든 뒤 실제로 뜨고 도는지 확인하는 순서다.

  1. 목록 확인 — 입력창에 / 를 쳐서 새 커맨드가 뜨는지, description 이 의도대로 보이는지 본다. 안 뜨면 파일 위치(.claude/commands/)와 확장자(.md)부터 확인한다.
  2. 실제 호출 — 안전한 커맨드부터 인자를 넣어 돌려 본다. 예: /check, 그다음 /git-commit 테스트.
  3. 권한 경계 확인 — allowed-tools 밖의 도구를 본문이 쓰려 하면 실행이 멈추고 권한 프롬프트가 뜬다. 이게 뜬다는 건 화이트리스트가 좁게 걸렸다는 정상 신호다. 자주 뜨면 필요한 명령을 allowed-tools 에 추가한다.
  4. 실패 진단 — 커맨드가 엉뚱하게 굴면 frontmatter 오타(특히 allowed-tools 필드명·명령 패턴)와 body 지시의 모호함을 의심한다.
증상의심 지점조치
/ 목록에 안 뜸파일 경로·확장자.claude/commands/<name>.md 위치와 .md 확인. YAML --- 구분선 누락도 점검.
매번 권한 프롬프트allowed-tools 누락/오타본문이 쓰는 명령을 화이트리스트에 추가. 필드명 철자(allowed-tools)와 Bash(git push:*) 패턴 확인.
인자가 안 먹힘body의 $ARGUMENTSbody에 $ARGUMENTS 치환·기본값 처리가 있는지 확인. 철자 정확히 대문자.
diff 전문을 다 읽어 느림body 지시 모호"--stat 요약만, 전문 읽지 말 것" 처럼 하지 말 것을 명시.
설명이 목록에서 빔description 누락frontmatter에 description 한 줄 추가.
주의

권한 프롬프트는 버그가 아니라 allowed-tools 가 제대로 걸렸다는 증거다. 성가시다고 무작정 Bash 로 통째 열지 말고, 실제로 필요한 명령만 골라 화이트리스트에 더하라. 좁은 권한이 곧 안전이다.
